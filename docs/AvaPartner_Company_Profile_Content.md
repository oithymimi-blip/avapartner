## 5. Security, Fund Protection, KYC & Blockchain Architecture

Security at AvaPartner is engineered as a **five-layer defense-in-depth framework** protecting user credentials, identity records, wallet custody, automated commission ledgers, and on-chain settlements.

### 5.1 Layer 1 — Account & Authentication Security
- **Cryptographic Password Hashing:** All user and administrator passwords are secured with **bcrypt** (salt rounds = 10).
- **Signed Stateless Sessions:** Authenticated sessions rely on **JSON Web Tokens (JWT)** signed with dedicated server secrets (7-day expiry) and enforced via strict middleware checks (`requireAuth`, `requireAdminRole`).
- **One-Time Password (OTP) Registration & Recovery:** Email registration supports 6-digit OTP verification (10-minute expiry), while password recovery issues single-use UUID tokens expiring in 30 minutes.
- **Role-Based Admin Isolation:** Administrative operations are protected by granular permission scopes (`admin` vs. `subadmin` permissions matrix), ensuring separated operational duties.
- **HTTP Transport Hardening:** Backend APIs enforce **Helmet** HTTP security headers and strict JSON payload boundaries.

### 5.2 Layer 2 — Two-Factor Authentication (Google Authenticator TOTP)
Users can activate **Google Authenticator (2FA)** directly inside the Security Center (`/security`):
- Uses a cryptographically generated **20-byte TOTP secret** paired via standard `otpauth://` QR codes or manual setup keys.
- Once enabled, **every withdrawal request strictly requires a fresh 6-digit TOTP verification code** before funds can be reserved or submitted.
- Disabling 2FA requires validating an active 6-digit authenticator code, preventing unauthorized account takeover.

### 5.3 Layer 3 — KYC / NID Identity Verification & Account Strength Scoring

### 5.4 Layer 4 — On-Chain Crypto Deposit Custody & Smart Contract Sweeping
AvaPartner utilizes an automated **BNB Smart Chain (BEP-20) USDT** deposit and treasury architecture:
- **Permanent Deterministic Deposit Addresses:** Each user is assigned a permanent, unique BEP-20 EVM wallet address derived deterministically via `keccak256` from the user's immutable account identity and server master key—meaning the deposit address never changes across logins, reloads, or redeployments.
- **EIP-1167 Minimal Proxy Forwarders (`Forwarder.sol` & `ForwarderFactory.sol`):** Supports lightweight cloned on-chain forwarder contracts capable of receiving BNB or BEP-20 tokens (`USDT: 0x55d398326f99059fF775485246999027B3197955`) and securely flushing funds only to the designated Treasury Hot Wallet (`owner` or `hotWallet` authorization enforced on-chain).
- **Multi-RPC Blockchain Redundancy:** Automated balance scanning rotates across 5 independent BSC RPC nodes (`publicnode`, `defibit`, `ninicoin`, `1rpc`, `binance.org`) every **20 seconds** (plus manual on-demand sync).
- **Strict Idempotent Accounting:** Deposits are tracked down to exact **Wei (`BigInt`) precision** (`unswept_credited_wei`) inside ACID SQLite transactions so no deposit can ever be double-credited or lost, followed by automatic gas-funded sweeping into the central Hot Wallet.

### 5.5 Layer 5 — Real-Time Cryptographic Withdrawal Address Validation & Data Integrity
- **Automatic Multi-Chain Checksum Verification:** Before any withdrawal is accepted, the platform runs synchronous cryptographic validation (`addressValidator.js`):
  - **BEP-20 / ERC-20 (`0x...`):** Validates 42-character hex structure, rejects burn/zero addresses (`0x000...000`), detects TRON/EVM network mismatches, and verifies **EIP-55 mixed-case Keccak-256 checksums**.
  - **TRON (`TRC-20`):** Validates 34-character `T...` format and performs full **SHA-256 Base58Check** checksum verification (`0x41` prefix).
  - **Bitcoin (`BTC`):** Validates **Bech32** (`bc1...`) SegWit checksums and **Base58Check** (`1...` / `3...`) addresses.
  - **Solana (`SOL`):** Validates 32-byte Base58 decoded length and rejects `0x` EVM addresses.
- **Atomic Balance Reservation & Auto-Refund:** Withdrawal amounts (minimum **$0.01 USDT**) are immediately reserved from the user's Available Balance and processed within a **3–24 hour SLA**. If a withdrawal is declined, both the reserved funds and any active bonus milestone state are automatically restored.
- **ACID Ledgers, Standardized BDT Time & Automated Backups:** All financial mutations execute in atomic database transactions (`better-sqlite3` WAL mode), log immutable entries to `activity_logs`, use standardized **Bangladesh Standard Time (BDT, Asia/Dhaka, UTC+6)** for unified auditability, and execute automated database snapshots every **6 hours** (retaining the latest 30 backups) plus graceful cloud persistence flushes on shutdown.
